# 上下行测速按钮设计

## 目的

给后续功能（传图片、文件这类大消息）选型：摸清这条 BLE 链路在**真实业务路径**上能跑多快，而不是线速上限。所以测速复用现有的 JSON 帧、现有分片和写应答，不加旁路通道。

入口是手机页面上的两颗按钮：「测上行」「测下行」，每次固定传 256 KB。

## 协议新增

帧格式不变。新增四种消息：

| 方向 | `t` | 载荷 | 含义 |
|---|---|---|---|
| 手机 → 电脑 | `benchup` | `v`：256 KB ASCII 字符串 | 上行测速数据，电脑只计数 |
| 手机 → 电脑 | `benchdown` | 无 | 请求下行测速 |
| 电脑 → 手机 | `benchdata` | `v`：256 KB ASCII 字符串 | 下行测速数据，手机丢弃 |
| 电脑 → 手机 | `benchend` | `bytes`：整数，`chunk`：整数 | 下行测速结束 |

载荷用重复的可打印 ASCII，JSON 编码不产生转义，字节数与字符数一致，测量口径可预测。

一次测速就是一条 256 KB 的消息（不是拆成多条）。代价是这条消息传输期间独占写链 / 发送锁，心跳发不出去；这条代价由下面的看门狗改动兜住。

## 计时口径

- **上行**：手机从调用 `sendAsync` 开始计时，到最后一片收到 ATT 应答结束。窗口内包含 JSON 编码（256 KB 约几毫秒，可忽略）和整条写链，主体是 ATT 往返延迟——正是链路真实吞吐的决定因素。带响应写本来就要等 ATT 应答，发送方的时钟即真实节奏。
- **下行**：计时在**手机端**，从收到这一大帧的第一片起算，到帧拼齐为止。

原先打算在电脑端给下行计时，实测不成立：`notify_value_async` 返回时只是把数据交给了 Windows 的发送队列——256 KB 入队 0.4 秒，手机真正收完要 2.7 秒。所以 `benchend` 只通知结束，不带耗时。

速率按 `256 KB ÷ 秒数` 计算，页面显示到一位小数。

## 心跳看门狗必须改喂食点

现有实现里 `#noteAlive()` 只在 `#dispatch` 调用，也就是**整条消息拼齐才喂狗**。一条 256 KB 的下行消息要十几秒才拼齐，这期间：

- 手机端收不到任何完整消息，第 9 秒看门狗判链路已死，测速必然中断；
- 电脑端 `send_lock` 被整条消息占住，心跳也发不出来。而一帧的字节流必须原子发送，中途插入心跳帧会把大帧的载荷拆坏，这个锁不能松。

改法：把 `#noteAlive()` 从 `#dispatch` 挪到 `#onNotify`，语义改成「收到任何字节就说明链路活着」。死链路不会送来字节，这个判定不比原来宽松，只是更贴近实际含义。`#dispatch` 里那次调用删除，保留一处喂狗点。

这是本次唯一改动现有链路逻辑的地方。

## 手机端

- `BleClient` 新增 `sendAsync(message)`：与 `send()` 共用 `#queue`，返回写链的 Promise。仅在已宣布连接时使用。断线时写链里的帧会被静默跳过（`#writeFrame` 提前返回），所以 `#writeFrame` 改成返回「整帧是否写完」，`sendAsync` 发现没写完就 reject，避免把「没发出去」测成「飞一样快」。
- `BleClient` 新增 `onBench` 回调：`benchend` 到达时把 `{ bytes, chunk }` 交给页面。
- `#dispatch` 增加两个分支：`benchdata` 丢弃（不报「未知消息」），`benchend` 走 `onBench`。
- 页面新增一组按钮「测上行」「测下行」，未连接或测速中禁用。
- 测速中事件行实时显示进度：`测速中… 62%（18.3 KB/s）`，每 100 毫秒刷新一次。速率取「已传字节 ÷ 至今耗时」，是平均值，不逐片抖动。

### 进度从哪来

- **上行**：手机就是发送方，`#writeFrame` 每写完一片回调 `onProgress(已写, 总长)`。
- **下行**：电脑端在发大帧时插不进任何消息（帧必须原子发送），所以进度只能由手机从收到的字节算。`FrameDecoder` 暴露 `progress()`：半帧已收多少字节、按帧头的长度前缀算出总长；没有半帧时返回 null。`BleClient` 把它转给页面，页面只认总长不小于 256 KB 的帧。

两个方向的进度都表现为「已传字节 / 总长」，页面共用同一个渲染函数。
- 结果显示在事件行：`上行 256 KB / 30.7 秒 = 8.3 KB/s（单包 512 B）`，下行同款，`chunk` 取 `benchend` 里的值。
- 链路状态离开 `connected` 时清掉测速中状态，避免按钮永久禁用。

## 电脑端

- `benchup`：只记一行 `logger.info("上行测速：收到 %d 字节", len(v))`，不做别的。
- `benchdown`：在 `handle()` 里 `await` 先发一条 `benchdata`，再发 `benchend`。发送期间读循环被占住十几秒，此刻用户输入会积在 `incoming` 队列，测完再上屏——测速本来就要独占链路，可以接受。
- 载荷大小是两端各自的常量，`benchdown` 不带任何尺寸参数，电脑端不接受对端指定的大小。

## 失败路径

- 上行中途写失败：写链的 catch 触发 `#handleDrop`，测速 Promise 随之 reject，事件行报「上行测速中断」，链路断开重连。
- 下行中途分片失败：电脑中止本条消息剩余分片。手机端解码器卡在半个帧上，下一条消息（心跳、`benchend`）会被当成载荷吞掉，凑够长度后 JSON 解析失败，走现有的「接收数据解析失败 → 断开重连」兜底。测速不会出结果，但链路能自愈。
- 已知代价：测速期间正常输入排在 256 KB 消息后面，最长等十几秒。

## 上行分片从 180 字节改成 512 字节

第一次真机测速暴露出来的问题，顺手一起修：

- Chrome 的 `BluetoothRemoteGATTCharacteristic` 原型上**没有** `maxWriteWithResponseSize`（实测 `Object.getOwnPropertyNames` 里没有），代码一直走 `FALLBACK_WRITE_CHUNK = 180`，256 KB 要切 1457 片。
- 每片带响应写的往返约 60 毫秒，1457 片就是 87 秒——这才是「点了没反应」的真身。
- 实测 Chrome 硬性拒绝超过 512 字节的写（514 报 `InvalidModificationError: Value can't exceed 512 bytes`），512 稳定通过，且单包往返耗时与 180 字节相同（都是 60 毫秒左右）。链路 MTU 517（电脑端 `max_notification_size` 报 514）也印证了这一点。

所以单包用满 512：同样 256 KB 只要 512 片，约 31 秒，快 2.85 倍。这个改动影响所有上行消息，不只测速。

## 下行内容校验

第一轮测速只证明了「3.3 秒收完 262144 字节、JSON 能解析」，**没有证明内容对**。原来的载荷是 `0123456789abcdef` 循环，换两片、重复一片、丢一片都在长度前缀的允许范围内拼得出合法 JSON，速度看起来还一样快。下行的顺序保证目前是推论（链路层按序 + 服务端按序入队），不是实测。

改法是两件事一起做：

- **载荷随机化**：电脑端每次用 `secrets.token_bytes` 生成再 base64，262144 字符（base64 是纯 ASCII，无 JSON 转义，字符数即字节数；262144 能被 3 整除，不带补位）。每次不同，也顺带排除了「两端各自生成同一份固定载荷」这种耦合。
- **哈希验证**：电脑端算 `sha256(payload)`，随 `benchend` 下发；手机拿收到的 `v` 重算，比对。不一致就在事件行报「校验失败：收到 xxxx，应为 yyyy」。一致报「校验通过（xxxxxxxx）」。

上行不改：带响应写由 ATT 串行化，分片不可能并发，没有可验的乱序。

## 上行切无响应写（探针后转正）

先裸发探针：上行特征值临时加声明 `WRITE_WITHOUT_RESPONSE`，手机按 508 字节/片（4 字节序号＋载荷）无响应写连续裸发 256 KB，电脑端逐片记序号。一次跑出三个答案：517 片全到（零缺失）、4.09 秒（63 KB/s，停等的 8 倍）、零乱序——逐片 `await` 的提交纪律下没复现坑 4。

于是转正，不加序号/窗口/重传：

- 中间分片无响应写，最后一片带响应写。ATT 按序处理，最后一片的应答到达时前面分片必然已排空——一次写同时拿到整条消息的送达确认、下一条消息的排队栅栏、测速的真实终点。单片消息自然落在最后一片分支，行为不变。
- 写超时按片数放宽：基础 2 秒＋每片 25 毫秒（空口实测约 8 毫秒/片，3 倍余量）。
- 上行测速载荷也改随机＋自带 `sha256`，电脑端重算比对，失败发 `notice`。这是「提交纪律保序」这个赌注的持续金丝雀。

探针还留下两个教训，都源于同一件事——**手机端入队 2.0 秒、空口 4.09 秒，积压约 2 秒躺在手机侧协议栈里**：

- 本地任何「写完」回调（无响应写 resolve、`notify_value_async` 返回）都只表示入队，量不到空口速率；测速终点必须锚定对端信号。
- 积压把随后的带响应写应答压过 2 秒超时线，造成一次假断链（日志：`写入失败：等待 ATT 响应超过 2000 毫秒`，2 秒后自动重连恢复）。

## 不做的事

- 不加测速专用特征值，不走旁路原始字节。
- 不改帧格式。上行分片从 180 字节改成 512 字节（见下节），下行 512 字节的夹紧策略不动。
- 不给网页端 `FrameDecoder` 加长度上限（与本次无关，另议）。
- 不给测速计时写自动化测试：它本质是 I/O 计时，单测覆盖不了真实链路，靠真机验收。`FrameDecoder.progress()` 是纯解码逻辑，照常补了单测。

## 验收

改完由用户真机点击验收，观察：

1. 事件行出现「测速中… 百分比（实时速率）」，百分比单调上涨，结束后换成上行 / 下行最终速率。
2. 电脑端日志出现「上行测速：收到 262144 字节」与下行对应的一行。
3. 测速全程不断连（看门狗不再误杀）。
4. 测速结束后键盘输入、剪贴板照常。
5. 未连接时两颗按钮禁用。
6. 下行结果行末尾出现「校验通过（xxxxxxxx）」；连续点几次，每次的哈希都不同。
