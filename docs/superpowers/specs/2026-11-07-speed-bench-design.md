# 上下行测速按钮设计

## 目的

给后续功能（传图片、文件这类大消息）选型：摸清这条 BLE 链路在**真实业务路径**上能跑多快，而不是线速上限。所以测速复用现有的 JSON 帧、现有分片和写应答，不加旁路通道。

入口是手机页面上的两颗按钮：「测上行」「测下行」，每次固定传 256 KB。

## 协议新增

帧格式不变。新增四种消息：

| 方向 | `t` | 载荷 | 含义 |
|---|---|---|---|
| 手机 → 电脑 | `benchup` | `v`：256 KB ASCII 字符串 | 上行测速数据，电脑只计数 |
| 手机 → 电脑 | `benchdown` | 无 | 请求下行测速 |
| 电脑 → 手机 | `benchdata` | `v`：256 KB ASCII 字符串 | 下行测速数据，手机丢弃 |
| 电脑 → 手机 | `benchend` | `bytes`：整数，`ms`：整数，`chunk`：整数 | 下行测速结果 |

载荷用重复的可打印 ASCII，JSON 编码不产生转义，字节数与字符数一致，测量口径可预测。

一次测速就是一条 256 KB 的消息（不是拆成多条）。代价是这条消息传输期间独占写链 / 发送锁，心跳发不出去；这条代价由下面的看门狗改动兜住。

## 计时口径

两边都以**发送方**的墙钟时间为准：

- **上行**：手机从调用 `sendAsync` 开始计时，到最后一片收到 ATT 应答结束。窗口内包含 JSON 编码（256 KB 约几毫秒，可忽略）和整条写链，主体是 ATT 往返延迟——正是链路真实吞吐的决定因素。
- **下行**：电脑从进入通知循环开始，计时到最后一包发完，把毫秒数放进 `benchend` 回报。

速率按 `256 KB ÷ 秒数` 计算，页面显示到一位小数。

## 心跳看门狗必须改喂食点

现有实现里 `#noteAlive()` 只在 `#dispatch` 调用，也就是**整条消息拼齐才喂狗**。一条 256 KB 的下行消息要十几秒才拼齐，这期间：

- 手机端收不到任何完整消息，第 9 秒看门狗判链路已死，测速必然中断；
- 电脑端 `send_lock` 被整条消息占住，心跳也发不出来。而一帧的字节流必须原子发送，中途插入心跳帧会把大帧的载荷拆坏，这个锁不能松。

改法：把 `#noteAlive()` 从 `#dispatch` 挪到 `#onNotify`，语义改成「收到任何字节就说明链路活着」。死链路不会送来字节，这个判定不比原来宽松，只是更贴近实际含义。`#dispatch` 里那次调用删除，保留一处喂狗点。

这是本次唯一改动现有链路逻辑的地方。

## 手机端

- `BleClient` 新增 `sendAsync(message)`：与 `send()` 共用 `#queue`，返回写链的 Promise。仅在已宣布连接时使用；`#link` 为空时同步抛错，由调用方按「链路未就绪」处理。
- `BleClient` 新增 `onBench` 回调：`benchend` 到达时把 `{ bytes, ms, chunk }` 交给页面。
- `#dispatch` 增加两个分支：`benchdata` 丢弃（不报「未知消息」），`benchend` 走 `onBench`。
- 页面新增一组按钮「测上行」「测下行」，未连接或测速中禁用。
- 测速中事件行显示「测速中…」。
- 结果显示在事件行：`上行 256 KB / 12.4 秒 = 20.6 KB/s（单包 514 B）`，下行同款，`chunk` 取 `benchend` 里的值。
- 链路状态离开 `connected` 时清掉测速中状态，避免按钮永久禁用。

## 电脑端

- `benchup`：只记一行 `logger.info("上行测速：收到 %d 字节", len(v))`，不做别的。
- `benchdown`：在 `handle()` 里 `await` 先发一条 `benchdata`，再发 `benchend`。发送期间读循环被占住十几秒，此刻用户输入会积在 `incoming` 队列，测完再上屏——测速本来就要独占链路，可以接受。
- `bytes` 字段从对端来，按信任边界夹到 `MAX_FRAME_BYTES` 以内，防止对端索取 GB 级内存。

## 失败路径

- 上行中途写失败：写链的 catch 触发 `#handleDrop`，测速 Promise 随之 reject，事件行报「上行测速中断」，链路断开重连。
- 下行中途分片失败：电脑中止本条消息剩余分片。手机端解码器卡在半个帧上，下一条消息（心跳、`benchend`）会被当成载荷吞掉，凑够长度后 JSON 解析失败，走现有的「接收数据解析失败 → 断开重连」兜底。测速不会出结果，但链路能自愈。
- 已知代价：测速期间正常输入排在 256 KB 消息后面，最长等十几秒。

## 不做的事

- 不加测速专用特征值，不走旁路原始字节。
- 不改帧格式，不动 `maxWriteWithResponseSize` / 512 字节分片策略。
- 不给网页端 `FrameDecoder` 加长度上限（与本次无关，另议）。
- 不加自动化测试：测速逻辑本质是 I/O 计时，单测覆盖不了真实链路，靠真机验收。

## 验收

改完由用户真机点击验收，观察：

1. 事件行出现「测速中…」，结束后出现上行 / 下行速率。
2. 电脑端日志出现「上行测速：收到 262144 字节」与下行对应的一行。
3. 测速全程不断连（看门狗不再误杀）。
4. 测速结束后键盘输入、剪贴板照常。
5. 未连接时两颗按钮禁用。
